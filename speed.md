# Speed estimation from a single rear-line camera

## Цель

Определять скорость волейбольного мяча по видео с одной статической камеры, установленной за задней линией.

Используем одновременно:

- координаты центра мяча на кадре;
- размер мяча в пикселях;
- геометрию волейбольной площадки;
- известные реальные размеры площадки;
- положение и высоту сетки;
- физическую модель полёта мяча;
- FPS видео.

Основной принцип:

> размер мяча не должен быть единственным способом оценки глубины. Он используется как дополнительное ограничение вместе с геометрией площадки и моделью траектории.

# 1. Входные данные

## 1.1. Разметка площадки

Файл:

```text
pro-bl-tula-demo_001_court.json
```

Кадр:

```text
1280 x 720
```

Опорные точки:

```text
0  home/back_left
1  far/back_left
2  far/back_right
3  home/back_right
4  center_left
5  center_right
6  net_left
7  net_right
```

Реальная геометрия пляжной площадки:

```text
ширина: 8 м
длина: 16 м
сетка: Y = 8 м
```

Высоту точек `net_left` и `net_right` необходимо задать явно.

Например:

```text
Z_net = 2.43 м
```

если размечена верхняя точка сетки / антенны.

---

## 1.2. Разметка мяча

Для каждого кадра используются:

```text
frame
cx
cy
w
h
```

где координаты bbox нормализованы.

Перевод в пиксели:

```python
u = cx * frame_width
v = cy * frame_height

w_px = w * frame_width
h_px = h * frame_height
```

Центр мяча:

```text
(u, v)
```

Оценка наблюдаемого диаметра:

```python
d_px = min(w_px, h_px)
```

`min(w, h)` предпочтительнее среднего размера bbox, потому что motion blur обычно растягивает изображение мяча вдоль направления движения.

В дальнейшем лучше перейти от bbox к:

```text
cx
cy
radius
radius_confidence
```

или к сегментационной маске мяча.

# 2. Система координат площадки

Использовать мировую систему координат:

```text
X — поперёк площадки
Y — от ближней задней линии к дальней
Z — вверх
```

Например:

```text
P0 = (0,  0, 0)
P3 = (8,  0, 0)

P1 = (0, 16, 0)
P2 = (8, 16, 0)

P4 = (0,  8, 0)
P5 = (8,  8, 0)
```

Если точки 6 и 7 находятся сверху сетки:

```text
P6 = (0, 8, 2.43)
P7 = (8, 8, 2.43)
```

Такой набор точек позволяет определить положение камеры относительно площадки.

---

# 3. Калибровка камеры

Нужно получить:

```text
K — intrinsic matrix
R — rotation
t — translation
dist — distortion coefficients
```

Минимальная цель:

```text
pixel (u,v) <-> луч камеры в мировой системе координат
```

Для статической камеры калибровка выполняется один раз.

## Вариант A — известны intrinsics

Если известны:

```text
fx
fy
cx
cy
distortion
```

использовать:

```python
cv2.solvePnP(...)
```

по 3D-точкам площадки и их 2D-разметке.

## Вариант B — intrinsics неизвестны

Можно начать с приближённой модели:

```text
fx ≈ fy
principal point ≈ центр кадра
distortion = 0
```

и совместно оптимизировать:

```text
f
R
t
```

по известной геометрии площадки.

Для получения точной скорости желательно выполнить обычную camera calibration отдельно.

---

# 4. Луч через центр мяча

Для каждой точки:

```text
pixel = (u, v)
```

строим луч:

```math
r = K^{-1} [u, v, 1]^T
```

После применения ориентации камеры:

```text
P(lambda) = C + lambda * r_world
```

где:

```text
C      — положение камеры
lambda — неизвестная глубина
```

Центр мяча определяет направление, но не определяет расстояние от камеры.

---

# 5. Начальная оценка глубины по размеру мяча

Реальный диаметр волейбольного мяча:

```text
D_ball ≈ 0.21 м
```

Для pinhole camera:

```math
Z_size ≈ f * D_ball / d_px
```

где:

```text
f     — фокусное расстояние в пикселях
d_px  — диаметр мяча в изображении
```

Это использовать только как `depth prior`.

Причина:

при мяче размером около 20 px ошибка всего в 1 px уже даёт ошибку глубины порядка нескольких процентов.

Дополнительные источники ошибки:

- motion blur;
- bbox detector;
- частичное перекрытие;
- неидеальная форма bbox;
- rolling shutter;
- defocus;
- compression artifacts.

---

# 6. Не вычислять скорость между соседними 3D-точками

Плохой вариант:

```python
speed = distance(P[i], P[i-1]) * fps
```

Такой расчёт очень чувствителен к ошибке глубины.

Даже небольшое дрожание `Z` приводит к огромным скачкам скорости.

Вместо этого необходимо сначала аппроксимировать участок траектории.

---

# 7. Разделение траектории на сегменты

Один сегмент — свободный полёт мяча между событиями:

```text
serve -> receive
receive -> set
set -> attack
attack -> block/defense
...
```

Касание игрока является точкой разрыва модели.

Для каждого сегмента отдельно восстанавливаются:

```text
X0
Y0
Z0
Vx
Vy
Vz
t0
```

---

# 8. Физическая модель траектории

Для короткого участка полёта использовать:

```math
X(t) = X0 + Vx * t
```

```math
Y(t) = Y0 + Vy * t
```

```math
Z(t) = Z0 + Vz * t - 0.5 * g * t^2
```

где:

```text
g = 9.81 м/с²
```

На первом этапе сопротивлением воздуха можно пренебречь.

Для длинных и быстрых траекторий позднее можно добавить drag.

---

# 9. Оптимизация траектории непосредственно в image space

Не обязательно сначала независимо получать `(X,Y,Z)` для каждого кадра.

Более устойчивый вариант:

1. задать параметры 3D-траектории;
2. вычислить `P(t)` для каждого кадра;
3. спроецировать `P(t)` обратно в изображение;
4. сравнить с разметкой мяча.

Основная ошибка:

```math
E_pixel =
sum || project(P(t_i)) - (u_i, v_i) ||²
```

Это должен быть основной сигнал оптимизации.

---

# 10. Размер мяча как дополнительное ограничение

Для рассчитанной 3D-точки можно предсказать размер мяча:

```math
d_pred ≈ f * D_ball / Z_camera
```

Добавить:

```math
E_size =
sum robust_loss(d_pred - d_observed)
```

Вес этого ограничения должен быть значительно меньше веса точности центра.

Например:

```text
pixel center       — высокий вес
ball diameter      — средний/низкий вес
physics            — высокий вес
court constraints  — высокий вес
```

---

# 11. Ограничения площадки

Геометрия площадки даёт дополнительные сильные ограничения.

## Сетка

При пересечении плоскости сетки:

```text
Y = 8 м
```

Это помогает определить глубину.

Если наблюдаемая траектория пересекает изображение сетки, восстановленная 3D-точка в этот момент должна быть близка к:

```text
Y = 8
```

## Земля

Мяч не может иметь:

```text
Z < radius_ball
```

до момента касания земли.

## Разумные пределы

Можно ограничить:

```text
-2 < X < 10
-3 < Y < 19
0 < Z < 15
```

с небольшим запасом за пределами площадки.

---

# 12. Функция ошибки

Практический вариант:

```math
E =
w_pixel * E_pixel +
w_size  * E_size +
w_net   * E_net +
w_prior * E_prior
```

Физика уже заложена параметрической моделью траектории.

Использовать robust loss:

```text
Huber
Soft-L1
Cauchy
```

чтобы отдельные плохие bbox не ломали всю траекторию.

Подходящие инструменты:

```python
scipy.optimize.least_squares
```

или:

```python
torch.optim
```

---

# 13. Расчёт скорости

После fitting параметры скорости уже известны.

```math
Vx(t) = Vx
```

```math
Vy(t) = Vy
```

```math
Vz(t) = Vz - g*t
```

Модуль скорости:

```math
V(t) =
sqrt(
    Vx² +
    Vy² +
    (Vz - g*t)²
)
```

Перевод в км/ч:

```python
speed_kmh = speed_ms * 3.6
```

---

# 14. Какую скорость показывать

Нужно заранее определить метрику.

Полезно хранить:

```text
speed_at_start
speed_at_end
max_speed
mean_speed
```

Для подачи / атаки наиболее интересна скорость сразу после контакта:

```text
V_contact
```

Практически её можно получать как скорость fitted trajectory в первом кадре после обнаруженного касания.

# 15. FPS

Время кадра:

```python
t = frame_index / fps
```

FPS нельзя просто предполагать равным 25 или 30.

Нужно читать:

```text
fps
time_base
PTS
```

из исходного видео.

Лучше использовать реальные timestamps кадров, особенно если видео VFR.

# 16. Фильтрация bbox мяча

Перед fitting:

### Отбросить явные выбросы

Например:

```text
слишком большой bbox
слишком маленький bbox
нереальный скачок центра
резкое изменение размера
```

### Размер фильтровать отдельно

Рекомендуется:

```text
median filter
Savitzky-Golay
robust local regression
```

Но не следует сильно сглаживать `(u,v)` до trajectory fitting — физическая модель сама выполняет необходимое сглаживание.

---

# 17. Motion blur

При быстром мяче bbox может быть сильно вытянут:

```text
----------->
  ooooooooooooo
```

Поэтому:

```python
d_px = min(w_px, h_px)
```

лучше:

```python
d_px = sqrt(short_axis_1 * short_axis_2)
```

если используется ellipse / mask fitting.

Оптимальный будущий вариант:

1. сегментация мяча;
2. ellipse fitting;
3. направление движения из соседних кадров;
4. измерение диаметра перпендикулярно motion vector.

# 18. Оценка confidence

Для каждой рассчитанной скорости желательно возвращать:

```text
speed_kmh
confidence
```

Confidence можно строить из:

```text
число кадров сегмента
pixel reprojection error
ошибка размера мяча
число выбросов
длина траектории
качество calibration
```

Например:

```text
> 15 кадров + reprojection < 1 px -> high
8-15 кадров                          -> medium
< 8 кадров                           -> low
```

Числа нужно подобрать экспериментально.

# 22. Основные риски

Наиболее критичные ошибки:

1. неправильная camera calibration;
2. неизвестная высота net keypoints;
3. bbox мяча сильно зависит от motion blur;
4. ошибка центра мяча;
5. ошибочное разделение траектории в момент касания;
6. неверный FPS;
7. rolling shutter;
8. слишком короткий участок траектории.

Из них на первом месте:

```text
camera calibration
```

а не точность формулы скорости.

# Ключевой принцип

Финальная скорость должна вычисляться из **параметров восстановленной 3D-траектории**, а не из разности глубин между двумя соседними кадрами.

Схема:

```text
2D ball center ──────┐
                     │
ball diameter ───────┤
                     ▼
court geometry -> 3D trajectory fitting -> velocity -> km/h
                     ▲
gravity ─────────────┘
```

Размер мяча используется как дополнительный источник информации о глубине, но геометрия и временная согласованность всей траектории имеют более высокий приоритет.
